## Project overview

**adjCOADD** is a large Django 4.1 application for **CO-ADD's microorganism database** (The University of Queensland's Community for Open Antimicrobial Drug Discovery). It manages microbiology domain data (organisms, cells, drugs, genes, peptides, compounds) and screening data (plates, samples, screens, collaborators), organised as a **multi-app, multi-database-schema** MVT project with **htmx-enhanced templates**.

- Version: `1.8.3` (dev), per `settings.py`
- Git branch: `dev_jzg` (remote: `development`)
- ~47,300 lines of Python (excl. migrations), ~10,000 lines of HTML templates, 55 migrations

## Architecture

### 1. Multi-database routing via PostgreSQL schemas

The defining feature is a **single PostgreSQL database, many schemas** — one per app — with a custom router in `routers.py`. Each app's tables live in its own `search_path`, giving logical separation without separate DB servers. Settings define a `DATABASES` entry per app alias (`settings.py`) and each view specifies its `transaction_use` (e.g. `'dorganism'`).

### 2. Core base model: `AuditModel`

Nearly every model inherits `AuditModel` in `apputil/models.py`, which provides:

- **Audit fields** — `astatus` (soft-delete status −9…2), `acreated/updated/deleted_at`, and FK audit users
- **Soft delete** via `remove()` (sets `astatus = -9`) instead of hard delete
- **ID generation** — `next_id()` uses `django-sequences` with per-class `ID_PREFIX`/`ID_PAD`
- **`save()` interception** — auto-stamps the creating/updating user
- **Generic table rendering helpers** — `LIST_VIEW_FIELDS`, `CARDS_FIELDS`, `get_fields()`, `get_values()`, `get_fieldsandvalues()` power the generic datatable/card templates, including dotted foreign-key traversal and `{VALUE1}` URL templating from `constants.py`

### 3. Shared base views & filters

`applib/django/base/views.py` defines the generic CRUD machinery all apps reuse:

- `Base_CreateView` / `Base_UpdateView` / `Base_RemoveView` — form-based CRUD with per-schema atomic transactions + `ApplicationLog` audit
- `Htmx_UpdateView` — inline row editing via `PUT` requests and partial templates
- `Filtered_ListView` — list views with session-cached querysets, multi/single filtering, pagination, and ordering
- `File_CreateView` / `Base_DataExportView` — file upload (AJAX + form) and CSV/pandas export

`applib/django/base/filters.py` provides `Base_Filter`/`BaseStatus_Filter` (django-filter with deep multi-field search, trigram similarity, and choice filters).

### 4. `Dictionary` pattern

Rather than fixed choices, most controlled vocabularies are rows in the `Dictionary` model, grouped by `dict_class` (e.g. strain type, MTA status, drug class). Forms and filters query `Dictionary.get_filterobj()`/`get_aschoices()` dynamically — this is the project's "lookup table" convention.

### 6. Request flow (MVT)

1. URL routes land in each app's `urls.py`, included from `adjcoadd/urls.py`
2. Class-based list views (`Filtered_ListView`) or function-based create/detail views render templates like `dorganism/organism/organism_list.html`
3. Templates `{% include %}` shared partials (datatables, modals, cards) with context fields computed by `model.get_fields()`
4. POST/PUT handled by base views with schema-scoped `transaction.atomic` and `ApplicationLog` audit writes

## htmx integration

htmx 1.8.4 is loaded from CDN in `scripts.html` and CSRF is injected globally in `base.html` via an `htmx:configRequest` listener. Patterns:

- **Inline row editing** — datatable templates put `hx-target="closest tr" hx-swap="outerHTML"` on `<tbody>`; `update_btn_htmx.html` and `cancel_btn_htmx.html` fire `hx-get`/`hx-put` against `Htmx_UpdateView` endpoints
- **Modal create/update** — `createModel_partial_modal.html` and `updateModel_partial_modal.html` load forms into modal bodies
- **Progress polling** — `progress_partial_modal.html` and `process_page.html` use `hx-trigger="load delay:500ms"` and custom events for long-running import/process tasks
- **System info** — the navbar loads version/DB info via `hx-get="system_info"`

## Frontend structure

- Shared templates in `templates/`: `base.html`, `navbar.html`, `home.html`, plus reusable `datatable/`, `modal/`, `cardview/`, `grid/`, `button/`, `process/`, `utils/`
- Per-app templates live in each app's own `templates/<app>/…` (Django `APP_DIRS: True`)
- The `zdoc/application_template/` directory is a ready-made scaffold for adding new model apps following the project's conventions

## Configuration & deployment

- `settings.py` switches environment via `DEVELOPMENT` (`None`=prod, `Test`, `Work`, `Local`, `Meran`)
- LDAP auth against `ldap.uq.edu.au`, custom user model `apputil.ApplicationUser`, session-expiry + idle middleware
- Backup cron (`apputil.utils.cron.Backup_adjCOADD`), logging to `applog/`
- `zdoc/` holds full setup/deployment docs (`Setup_COADD_Application.md`, `Setup_PostgreSQL.md`) and systemd/nginx configs

## Testing

Tests exist under `tests/` (`unit_tests/test_apputil`, `test_ddrug`, `test_dorganism`, `test_dplate`) plus per-app `tests.py`. Coverage is thin relative to code size. I did **not** execute them — the project requires a live PostgreSQL instance with the per-app schemas and LDAP configuration, which isn't available in this environment.

## Notable observations / potential issues
